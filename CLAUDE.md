# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This is a single repository holding an Express backend and an Angular frontend as a subdirectory. There is no real business logic in the Express scaffold itself yet — update this file as the project takes shape.

1. **Root app** (`app.js`, `bin/`, `routes/`, `views/`, `public/`) — a stock Express 4 app generated by `express-generator`, using Jade templates. `routes/index.js` and `routes/users.js` are still the generator's defaults ("respond with a resource", etc.) and haven't been customized. `routes/api.js` is a real JSON API — it connects this app to the Angular frontend and drives the jobup.ch login and CV-match automations (see below).
2. **`frontend/`** — an Angular 21 SSR application, tracked as a plain subdirectory of this repo (not a nested git repo). See `frontend/CLAUDE.md` for its commands and architecture.
3. **`scripts/jobup-login.js`** — a standalone Playwright script, spawned as a child process by `routes/api.js`, that logs into jobup.ch (see below). Exports `dismissCookieConsent`/`performLogin`/`loginToJobup` so `scripts/jobup-cv-match.js` can reuse the login flow on its own page/browser instead of duplicating it; only runs as a CLI (reading env vars, printing JSON to stdout) when invoked directly.
4. **`scripts/jobup-cv-match.js`** — a standalone Playwright script, spawned as a child process by `routes/api.js`, that logs into jobup.ch (reusing `scripts/jobup-login.js`), runs a profile-based job search, opens the AI CV-match analysis for the first result, and posts the analysis text back to the backend (see below).
5. **`tests/`** — root-level Playwright e2e suite. Includes a spec that drives the same jobup.ch login *page* (navigation only, no credentials) for e2e coverage — separate from the `scripts/jobup-login.js`/`scripts/jobup-cv-match.js` automations used by the live features.

## Backend ↔ frontend connection

The Express app now serves a small JSON API, and the Angular app calls it:

- `routes/api.js` mounts `GET /api/health` (returns `{ status, service, timestamp }`).
- `app.js` mounts that router at `/api` and applies CORS scoped to that path, allowing `http://localhost:4200` (the Angular dev server) to call it directly.
- `frontend/proxy.conf.json` proxies `/api/*` requests from the Angular dev server to `http://localhost:3000`, wired up via `proxyConfig` in `frontend/angular.json`'s `serve` target — so in practice CORS is a fallback and the proxy is the normal dev path.
- `frontend/src/app/services/api.ts` (`Api` service) calls `/api/health` via `HttpClient`; `frontend/src/app/app.ts` calls it on init and renders the result (`backendStatus` signal) in `app.html`.

**To see it working**: run `npm start` at the root (Express on port 3000) and `npm start` in `frontend/` (Angular dev server on port 4200) at the same time, then open `http://localhost:4200` — it should show "Backend status: connected".

This wiring only covers local development (the dev-server proxy and CORS for `localhost:4200`). There's still no production integration — nothing yet decides whether Express serves the built Angular app, proxies to it, or the two are deployed as fully separate services.

## jobup.ch login automation

The frontend has a "Login" button (`frontend/src/app/app.html`/`app.ts`) that triggers a real login attempt against jobup.ch through the backend:

1. Button click → `Api.login()` (`frontend/src/app/services/api.ts`) → `POST /api/login`.
2. `routes/api.js`'s `/login` handler spawns `scripts/jobup-login.js` as a **child process** (`child_process.execFile`) and awaits it.
3. `scripts/jobup-login.js` launches a headless Chromium browser via Playwright, drives jobup.ch's actual login flow using `JOBUP_EMAIL`/`JOBUP_PASSWORD` from the environment, and prints one line of JSON to stdout: `{"success": true|false}`.
4. The Express handler parses that JSON and responds with `{ success, message: "Login succeeded !" }` or `{ success, message: "Login failed !" }`, which the frontend displays next to the button.

**Setup**: copy `.env.example` to `.env` at the repo root and fill in real jobup.ch credentials (`JOBUP_EMAIL`, `JOBUP_PASSWORD`). `app.js` loads it via `dotenv` at startup. `.env` is gitignored — never commit real credentials. `playwright` is a direct production dependency (not just a transitive devDependency of `@playwright/test`) specifically so this script keeps working in a production install.

**How the flow was reverse-engineered** (useful if jobup.ch changes and selectors need updating): jobup.ch has two different cookie-consent variants that appear inconsistently between sessions — a plain `alert` with an exact-text "ok" button, and a fuller GDPR `dialog` with a "Accepter tous les cookies" button; `scripts/jobup-login.js` checks for both. The "Se connecter" control is a `<button>` (`id="user-nav-login-link"`), not a link — clicking it opens an Auth0-hosted universal-login flow at `auth.jobup.ch` with no stable URL to `goto()` directly. That flow is two-step: an email textbox ("Adresse e-mail") + a "Continuer" button (use `exact: true` — there are also "Continuer avec Google"/"Continuer avec Apple" buttons that substring-match "Continuer"), then a password textbox ("Mot de passe") + the same "Continuer" button. On failure the page shows the text "E-mail ou mot de passe incorrect" and stays on `auth.jobup.ch`; on success it redirects away from that host. The script races those two outcomes with a 20s timeout.

**Gotcha already hit once**: the cookie-consent overlay fades in over ~200ms, so checking it with `.isVisible({ timeout })` is unreliable — that method checks immediately rather than actually waiting for the element to appear, so it can return `false` before the dialog has mounted, silently skip both branches, and then the overlay blocks every subsequent click (including "Se connecter") until Playwright's default 30s action timeout is exhausted. Use `.waitFor({ state: 'visible', timeout })` instead (raced across both variants with `Promise.race`), which properly waits. Both `scripts/jobup-login.js` and `tests/jobup-login.spec.ts` use this pattern now — don't reintroduce `.isVisible()` for this check.

**Known limitation**: this drives Auth0's real, live login form, so any change to its markup, copy, or flow (or a CAPTCHA/rate-limit challenge triggered by too many automated attempts in a short window) can break the selectors or the success/failure heuristic above. Re-derive them the same way this was built: run the script directly (`JOBUP_EMAIL=... JOBUP_PASSWORD=... node scripts/jobup-login.js`) and inspect `page.locator('body').ariaSnapshot()` at each step rather than guessing.

## jobup.ch CV-match automation

`scripts/jobup-cv-match.js`, triggered via `POST /api/cv-match`, extends the login automation into a full job-search + AI CV-match flow. Every selector below has been verified end-to-end against the live site (each was wrong at least once first — see "Selector gotchas" below for what jobup.ch's markup actually looks like and why the obvious guess didn't work).

1. Logs into jobup.ch by reusing `dismissCookieConsent`/`performLogin` from `scripts/jobup-login.js` (same page/browser, not a second process), then navigates to `https://www.jobup.ch/fr/emplois/`.
2. Clicks "Rechercher avec mon profil" — or, if `useBasicSearch` is true (from `POST /api/cv-match`'s body, defaulting to false; the frontend's "Use basic search" checkbox next to the CV Analysis button), skips straight to the "Recherche d'emploi" sub-nav tab / basic-search entry point instead (mainly useful for exercising/testing that path directly without depending on account state). Either way, `/fr/emplois/` can independently render in "Intelligent search" mode (broader/semantic results, sparkle "Recherche" button) or "Basic search" mode (the classic filter UI, narrower/literal results), regardless of entry point — see the search-mode-detection gotcha below for how the script detects and handles both: `useBasicSearch` true goes straight to Basic search mode and `RECOVERY_SEARCH_TERM`; the natural sub-nav-tab fallback (CTA/role unavailable, `useBasicSearch` false) detours through Intelligent search mode looking for "Rechercher avec mon profil" there, and if that's not found either, navigates directly to the results URL with `term=<RECOVERY_SEARCH_TERM>&location=<LOCATION_SLUG>` set as query params — staying in Intelligent search mode rather than falling back to Basic search mode, since Intelligent mode returns substantially more results for the same term/location (confirmed live: ~195 vs. ~18). Otherwise (when a term field was actually filled through the UI), once page 1's results render (confirming the URL has synced with the real `term`), applies a location filter by navigating to that URL with `location=<LOCATION_SLUG>` appended (see the location-filtering gotcha below for why this replaced clicking "Utiliser ma localisation", and why it only works on the basic-search path). Reads the total match count from the "... offres d'emploi" text near the top of the page as `totalJobsCount` (a supplementary value — logs and continues with `null` if it can't be found/parsed, doesn't fail the run).
3. Selects the `jobIndex`-th (1-based, across all result pages) job offer (`jobIndex` comes from `POST /api/cv-match`'s body, defaulting to 1; a non-positive-integer index returns `{ success: false, analysis: null, jobUrl: null }` immediately). First waits for page 1's results to actually render. jobup.ch paginates at `JOBS_PER_PAGE` (20) per page: an index beyond the first page reaches the right page (`targetPage = Math.ceil(jobIndex / 20)`) either by navigating directly to `?page=<targetPage>` (basic-search recovery path) or by clicking a "next page" control repeatedly, once per intermediate page (direct-CTA path) — see the pagination gotcha below for why the two paths need different approaches here. Then selects position `((jobIndex - 1) % 20) + 1` *within* that page (not the simpler `jobIndex % 20`, which would give an invalid position 0 for exact multiples of 20); if that position exceeds the number of jobs actually found there, returns the same `{ success: false, ... }` shape. Reads the selected job's real detail-page URL (`https://www.jobup.ch/fr/emplois/detail/...`) from the link's `href` attribute *before* clicking it as `jobUrl` — jobup.ch renders the job detail in place rather than navigating there (it just adds a `?jobid=...` query param to the *listing* page's URL), so `page.url()` after the click would be the wrong thing to use here.
4. If that job was already analyzed in a previous run, jobup.ch shows a "Voir l'analyse" button (read the existing result) instead of "Voir mon match" (run a new analysis, then confirm with "Continuer") — the script detects and handles both.
5. Waits (up to 60s for a new analysis, 20s for an existing one) for the "Fermer" button on the analysis dialog to appear as the signal that the result is ready, reads the dialog's text as the analysis result, `POST`s it as `{ analysis }` to `${BACKEND_URL}/api/cv-analysis` (`BACKEND_URL` defaults to `http://localhost:3000`), then clicks "Fermer".
6. Prints `{"success": true|false, "analysis": string|null, "jobUrl": string|null, "totalJobsCount": number|null}` to stdout, same convention as `scripts/jobup-login.js`.

`routes/api.js`'s `POST /cv-analysis` handler is the receiving end: it just validates and `console.log`s the analysis text (no persistence yet — revisit if this needs to be stored/displayed somewhere).

**Selector gotchas already hit** (each of these cost a full round trip against the live site — none of the obvious guesses matched jobup.ch's actual markup):
- "Rechercher avec mon profil" (the profile-search step) has an ambiguous accessible name on `jobup.ch/fr/emplois/` — a `getByRole('button', { name: /rechercher avec mon profil/i })` locator matches *two* buttons (a Playwright strict-mode violation): a nested button inside the "Ouvrir Recherche" search-bar dropdown (`data-cy="search-with-profile-button-row"`) and the standalone page CTA (`data-cy="search-with-profile-button-cta"`). The script targets the CTA by `data-cy` first (25s wait — it's occasionally been slow to render, even within the same session where it worked moments earlier, so this favors giving it time over falling back prematurely), then a plain `getByRole('button', { name: /rechercher avec mon profil/i }).last()` (15s). A logged-in account can also accumulate enough search/application history (e.g. 16+ "Candidatures" from repeated automation runs) that `/fr/emplois/` shows a candidate-dashboard sub-nav instead (`data-cy="vacancy-search-sub-nav"`, tabs "Recherche d'emploi" / "Recommandations d'emploi" / "Job Alerte" / "Emplois sauvegardés" / "Candidatures"), with no "Rechercher avec mon profil" text anywhere on the page — as a last resort the script clicks that sub-nav's "Recherche d'emploi" tab, which confirmed live has recurred even with the 25s CTA wait in place — so this really can be a persistent account state, not just page-load jitter. If you see `entered search flow via path: subNavTab` in the logs, that's expected recoverable behavior, not necessarily a failure — the whole run can still succeed (it has), just noticeably slower (one observed run took ~76s total vs. ~16s for a run that used the CTA directly). If later steps hit similar strict-mode violations, check for a `data-cy` attribute on the live element first — jobup.ch's markup has them — before falling back to broader role/text matching.
- **Search-mode detection ("Intelligent search" vs "Basic search")**: `/fr/emplois/` can independently render in "Intelligent search" mode (a free-text "Décris ton rôle idéal :" box, no "Villes ou régions" field) or "Basic search" mode (the classic filter UI, with "Villes ou régions" and the category filter bar) — confirmed live this isn't strictly tied to entry point (the sub-nav tab can land in either one, apparently depending on persisted account/browser state, not always the AI mode originally assumed). Whichever mode is *not* currently active offers a link to switch to the other, and the two links are mutually exclusive (only one is ever present): "Aller à la recherche intelligente" only while in Basic search mode, "Aller à la recherche basique" only while in Intelligent search mode. `scripts/jobup-cv-match.js` uses presence of these links (`switchModeIfLinkPresent()`) to detect and normalize the current mode rather than assuming it from `searchWithProfilePath`:
  - `useBasicSearch` true: ensures Basic search mode directly (switches if the "go to basic" link is present, no-op if already there) and uses `RECOVERY_SEARCH_TERM` — this is the explicit request for the basic-search flow, no CTA detour.
  - `useBasicSearch` false, natural sub-nav-tab fallback (CTA/role unavailable on the initial page): ensures Intelligent search mode first (switches if the "go to intelligent" link is present, no-op otherwise — now logged explicitly either way), then looks there for "Rechercher avec mon profil" — confirmed live it's often genuinely unavailable even in Intelligent search mode, in which case the script falls back to `RECOVERY_SEARCH_TERM`. When it *is* found, clicking it re-routes `searchWithProfilePath` to `'cta (via subNavTab detour)'` so all the downstream CTA-vs-basic branches (location filtering, pagination) treat it exactly like the direct-CTA path. **Gotcha hit here**: this lookup has the exact same ambiguous-accessible-name issue as `searchWithProfileByRole` at the top of the function (two matches: a hidden nested button inside the "Ouvrir Recherche" dropdown, plus the real standalone CTA) — an initial version used `.first()` here instead of the already-proven `data-cy="search-with-profile-button-cta"` / `.last()` combo, which silently resolved to the hidden element and always timed out, making the button look permanently unavailable even when present. Fixed to reuse the same data-cy-first-then-`.last()` strategy as the top-level cascade.
  - **Intelligent search mode returns substantially more results than Basic search mode for the *same* manually-typed term/location** — confirmed live via a user-supplied screenshot (a real browser, term="développeur", location="Genève", in Intelligent search mode's own dual-field UI, sparkle "Recherche" button) and matching automated runs: Intelligent mode returned `totalJobsCount: 195` for `term=développeur&location=Genève`, vs. `totalJobsCount: 18` for the identical term/location submitted in Basic search mode. An earlier version of this fallback switched to Basic search mode before filling `RECOVERY_SEARCH_TERM` (needlessly narrowing results ~10x) — fixed to stay in Intelligent search mode. But filling that term through the UI while staying in Intelligent search mode doesn't reliably work either: confirmed live, the state right after entering via the sub-nav tab can be the true free-text AI landing page, with no matching input/combobox/textbox at all and no "Recherche" button (that button/dual-field layout only appears once a search has actually been run — which is what the screenshot showed, and what any prior recovery run leaves behind, explaining why it worked in earlier tests but not from a fresh landing). So this fallback skips UI interaction entirely and navigates straight to the results URL with `term=<RECOVERY_SEARCH_TERM>&location=<LOCATION_SLUG>` set as query params (same reliable mechanism as the location-filtering and pagination gotchas below), then relies on `waitForJobResults()` — no term field, no "Recherche" click. A `skipSearchSubmit` flag in `scripts/jobup-cv-match.js` short-circuits the generic term-fill/"Recherche"-click/first-`waitForJobResults` steps for this case; the later location-filtering block still runs but no-ops since `location` is already set on the URL.
- The category filter bar (`Domaine d'activité`, etc.) is a row of collapsed dropdown triggers — each a `role="button"` element whose accessible name comes from its `title` attribute (e.g. `id="Domaine d'activité-trigger"`, `title="Domaine d'activité"`), duplicated in the DOM for responsive mobile/desktop layout (jobup.ch renders both and hides one via CSS, so locators matching by role/name alone can resolve to 2+ elements). It's part of the Basic search mode UI (see the search-mode-detection gotcha above) that the rest of the flow (term field, "Recherche" button, location filtering below) needs.
- The "Aller à la recherche basique" recovery UI's search ends up with an *empty* `term` query param — confirmed live: it returned `totalJobsCount` ~36000 vs. ~2500-3200 on the direct-CTA path for presumably the same profile, because that path's "Rechercher avec mon profil" auto-generates a profile-derived search term server-side that never reaches this recovery UI. There's no way for the script to know or reproduce that generated term, so instead it fills in a fixed keyword (`RECOVERY_SEARCH_TERM = 'développeur'` in `scripts/jobup-cv-match.js`) on this path only. The term field itself has no placeholder/aria-label/name — confirmed live via a diagnostic dump: `id="synonym-typeahead-text-field"`.
- **Applying "Utiliser ma localisation" by clicking through jobup.ch's UI was abandoned entirely after extensive live testing showed it's fundamentally unreliable, and replaced with direct URL navigation instead — but that replacement only works on one of the two search-entry paths.** For context, clicking through the UI failed in layered ways across multiple rounds of investigation: jobup.ch turned out to use two *different* location-field widgets depending on entry path (`id="location-pill-trigger"` on the direct-CTA path — a "pill" combobox with no standalone button at all, requiring a dropdown-option click that needed `click({ force: true })` to work around the "Domaine d'activité" chip persistently intercepting it — vs. `id="location-typeahead-text-field"` on the basic-search recovery path, which *does* have a standalone `<button title="Utiliser ma localisation">`, confirmed live via a user-supplied DOM dump); the standalone button could be entirely absent from the DOM until its field was focused first; and even a successful-looking click on either widget frequently left the actual search unfiltered by location (a "success" that produced no error was not the same as a real filter taking effect — the CTA path's own value stayed empty even on definite success, while the recovery path's value could become non-empty only to revert moments later). None of this was reliably fixable through more precise clicking.
  - **What actually works, confirmed live**: `location=<slug>` (`LOCATION_SLUG` in `scripts/jobup-cv-match.js`, currently `'Genève'`) is a real, server-recognized query param — appending it to the results URL and navigating there returns genuinely filtered, exactly accurate results (verified against a user-supplied expected count: `totalJobsCount: 17`, an exact match) — **but only on the basic-search recovery path**. This must happen *after* `waitForJobResults()` confirms page 1 has actually rendered (i.e. jobup.ch's asynchronous URL sync — see the pagination gotcha below — has already populated the real `term`), not immediately after clicking "Recherche", or the stale/bare URL read at that point gets permanently locked in once navigated to.
  - **What does not work, confirmed live**: the same approach on the direct-CTA path reliably throws `ERR_TOO_MANY_REDIRECTS` — re-navigating that same page via `page.goto()` to add `location=...` is incompatible with whatever session/routing state that path accumulates, matching the `page=N` pagination failure below. This was tested and ruled out as a URL-length issue specifically: the redirect loop persisted even with the `term` truncated to ~30 characters (down from the profile-derived original, often 300+). **Known, currently-unresolved limitation**: the direct-CTA path's searches are not location-filtered at all — the script logs `direct-CTA path: skipping location filtering` and proceeds with term-only results rather than pretending an ineffective click accomplished something. Use `useBasicSearch` (the frontend's "Use basic search" checkbox) when a location-filtered search is actually needed. A promising but unexplored next step, if this needs revisiting: opening a *new* page in the same authenticated browser context (shares login cookies, but none of the accumulated SPA state) and navigating that instead of the original page.
- The same job-link element can appear twice in the matched set on a single results page, at a very different `x` (e.g. 71 vs 454) — confirmed live on the basic-search recovery path — most likely a second rendering elsewhere on the page (a "recommended"/promotional widget also using `data-cy="job-link"`) rather than the main list itself duplicating entries. `dedupeByHref()` in `scripts/jobup-cv-match.js` removes later occurrences of a repeated `href` (keeping the first/topmost one) before the bounding-box sort runs, and logs any duplicates it removes.
- Job cards on the direct-CTA search UI have `data-cy="job-link"` — not `role="article"` and not a plain `a[href*="/emploi/"]` link (both were tried and found nothing live there). But confirmed live: the "Aller à la recherche basique" recovery path can land on a *different* results UI variant that uses `role="article"` cards instead, with zero `data-cy="job-link"` elements — seen when this went undetected: pagination's "next page" wait passed (it matches either pattern), but the final job count came back 0 because it was still hard-coded to only look for `data-cy="job-link"`, making a legitimately-in-range `jobIndex` wrongly report `success: false`. Fixed: `scripts/jobup-cv-match.js` now reads both `dataCyJobLinks` and `articleJobLinks` (via `.all()`) *after* arriving at the target page and uses whichever one is actually non-empty there, rather than assuming the pattern seen on page 1 (or either page) up front.
- Locator/DOM order (what `.count()`/`.nth()` follow) isn't guaranteed to match a job's actual top-to-bottom position on the page — jobup.ch has no known position/index attribute (nothing like `data-index`/`aria-posinset` seen in any live dump so far) to read this from directly, and its list could in principle virtualize or otherwise reorder cards in the DOM independent of visual layout. So job selection sorts the matched elements by their real on-screen position instead: `Promise.all(jobElements.map(el => el.boundingBox()))`, then sorts by `y` (then `x`) ascending, before indexing into that sorted array. The `data-cy` locator's `:visible` filter still matters here too — it keeps jobup.ch's responsive mobile/desktop markup duplication (see the filter-bar bullet above) from being included in the bounding-box sort at all. `runCvMatch()` unconditionally logs `job order on page N: [...]` (position/href/x/y for every matched element, plus any dropped for a null bounding box) — added after a `jobIndex = 20` run returned a job the user didn't expect, with no error. Confirmed live on a follow-up run: the returned `jobUrl` exactly matched that run's own `job order` dump at the expected position, with a clean list (no duplicates, nothing dropped, strictly increasing `y`) — so the sort/selection logic itself is correct. The original mismatch was almost certainly comparing two different searches (jobup.ch's live listings and/or the CV-derived search term can vary between runs), not a bug — "the Nth job" is only a stable target within the same run/search, not across separate ones.
- Right after paginating (clicking "next page"), every matched job element can briefly resolve with a null `boundingBox()` *at once* — hrefs already present, elements already matched by the locator, just still mid-render/settling — confirmed live on page 3 after two "next page" clicks. This previously got misread as "0 jobs on this page" (reporting an in-range `jobIndex` as out-of-range) rather than the transient state it actually was. `measureJobs()` in `scripts/jobup-cv-match.js` now retries the whole measurement (re-`.all()`, re-`boundingBox()`) up to 3 times, 750ms apart, whenever *every* matched element came back with no bounding box, logging each retry attempt, before trusting a fully-dropped result as genuinely empty.
- Clicking a job card doesn't navigate to a new page/tab — it updates the current page's URL with a `?jobid=...` query param and renders the job's details in place. The CV-match affordance on that detail view is state-dependent: a job never analyzed before shows "Voir mon match" (run a new analysis), but a job **already analyzed in a previous run** shows "Voir l'analyse" instead, and that state contains no text matching "match" anywhere on the page at all — which is what made the first several attempts at this step look like a broken selector when it was actually just a different, valid state. The script checks for both buttons via `Promise.race(...)` and handles each accordingly.
- The analysis result modal isn't the only `<dialog>` on the page at that point — a plain `getByRole('dialog')` is ambiguous (Playwright strict-mode violation): the "estimation in progress" placeholder modal (`data-cy="jobfit-pending-modal"`) stays mounted alongside the actual result modal (`data-cy="jobfit-analysis-modal"`). `readAnalysisAndClose()` in `scripts/jobup-cv-match.js` targets the result modal by that `data-cy` specifically.
- jobup.ch syncs the results URL (adding a profile-derived `?term=...`) *asynchronously* after clicking "Recherche" — reading `page.url()` immediately after that click can capture it before that sync happens. Confirmed live: doing so for pagination (appending `?page=2` to that stale/bare URL) navigated jobup.ch to a blank, unfiltered `/fr/emplois/` with zero results, not page 2 of the actual search. Fixed by waiting for page 1's results to actually render (`waitForJobResults()`) before doing anything else with them.
- Pagination via `&page=N` on the results URL is **path-dependent, the same split as the location-filtering gotcha above**: on the direct-CTA path, `page.goto()` to that URL throws `ERR_TOO_MANY_REDIRECTS` (that path's session/routing state, not a URL-length issue — same root cause as the location one), so `scripts/jobup-cv-match.js` paginates that path by clicking a "next page" control instead (`getByRole('link'|'button', { name: /suivant|next/i })`, **confirmed live** — used successfully to reach page 2 for jobIndex 25), once per page needed, re-running `waitForJobResults()` after each click, dumping pagination-area candidates (`data-cy*="pag"`, `nav`, `[aria-label*="pagination"]`, `[role="navigation"]`) to stderr if that selector ever stops matching. On the basic-search recovery path, though, **confirmed live `page=N` works fine as a direct `page.goto()`** (no redirect loop) — same as `location=` on that path — so the script uses that instead of clicking, appending `page=<targetPage>` to the URL and navigating once (not once per intermediate page), verified against jobIndex 25 (`targetPage` 2): the selected job's `href` exactly matched the expected in-page position in the resulting job-order dump.

Given how many of these needed a live round trip to pin down, treat any *still-unverified* step (there shouldn't be any left after the above, but jobup.ch can change) the same way: don't just guess a fix — dump the actual live DOM (`data-cy` values, button texts, `page.locator('body').ariaSnapshot()`) to stderr on failure first, then fix based on what that shows.

## Architecture notes

- **Root Express app**: classic MVC-ish layout — `app.js` wires middleware and mounts routers from `routes/`, `bin/www` creates the HTTP server and normalizes the port, views render with Jade from `views/`. Static assets are served from `public/`.
- **Playwright**: configured at the root (`playwright.config.ts`) with `testDir: './tests'`, running against chromium/firefox/webkit. No `baseURL`/`webServer` is configured, so specs must `page.goto()` a full URL. A GitHub Actions workflow (`.github/workflows/playwright.yml`) runs `npx playwright test` on push/PR to `main`/`master`.
  - `tests/example.spec.ts` is still the default template pointed at `playwright.dev`.
